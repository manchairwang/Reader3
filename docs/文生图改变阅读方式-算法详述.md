# 当每一页文字都配有画卷：面向移动阅读的实时文生图调度系统

——Reader3Pic 的算法设计与多维度分析

## 摘要

大模型文生图（Text-to-Image）能力的成熟，使"边读边画"成为可能：读者翻到任意一页，系统即时为该页文字生成一幅贴合情节的插画。然而把这项能力塞进一部手机、几家参差不齐的云服务与一台本地推理机之间，真正的难题不是"能不能画出图"，而是**调度**——如何在不触怒任何上游限流策略的前提下，让读者在翻页的间隙里恰好等到一幅图。本文以 Reader3Pic（基于开源阅读器 legado 的插图增强分支）为例，完整描述一套面向移动阅读场景的实时文生图调度系统：提示词聚合、多渠道竞速、模型级 ETA 调度、双层限流、阅读节奏自适应（稀疏生成与动态分辨率）、故障自愈与统计持久化，并从性能、体验、工程、成本四个维度给出分析。

---

## 一、为什么文生图会改变阅读方式

传统阅读的视觉通道只有文字。插图曾经是昂贵的：需要画家、排版与印刷周期，因此只有极少数书页拥有插画。文生图把插画的边际成本压到"一次 API 调用"，从此**每一页都可以有画**。

这改变了三件事：

1. **插画的粒度**：从"章"细化到"页"，插画不再是章节的装饰，而是页级内容的可视化摘要。
2. **插画的个性**：提示词由当前页文字实时生成，同一本书每位读者的插画序列都不完全相同。
3. **阅读节奏的耦合**：生图需要时间（数秒到两分钟），而翻页只需要一秒。**阅读速度与生图速度的失配**成为核心矛盾——这正是本文调度系统要解决的问题。

## 二、系统总览：从文字到插画的流水线

```
翻页事件
  └─> 页文本提取（章节+页内偏移做稳定 key）
       └─> 提示词构建（三段聚合）
            └─> 任务编排（稀疏步长过滤 + 失败退避过滤）
                 └─> 多渠道竞速生成
                      ├─ 云端：agnes(.cn/.com)、sensenova、NIM
                      ├─ 网关：win/cat omniroute（flux.1-schnell）
                      └─ 本地：qwen(sdcpp)、pony
                 └─> 并发闸 / 限流闸 / 健康检查（贯穿全程）
            └─> 结果缓存（内存 LRU + 磁盘）
                 └─> 展示（图片窗口 + 等待期马赛克背景）
```

贯穿始终的三个横切机制：**统计**（每服务器×模型延迟、阅读速度）、**限流**（并发闸+滑动窗口）、**自愈**（探活、恢复探测、失败补图）。

## 三、提示词工程：三段聚合算法

直接把整页小说原文丢给文生图模型，效果差且 token 昂贵。Reader3Pic 把提示词拆为三段聚合：

```
prompt = 聚合( 章节关键词, 页摘要, 风格词组 )

① 章节关键词 = LLM(当前章±1 三章全文)      → 按章缓存，只算一次
② 页摘要     = LLM(本页文字) 或 正则分句兜底  → 逐页生成
③ 风格词组   = 用户选择的插画风格            → 常量
```

**去重聚合规则**：拆分（逗号/分号/换行）→ trim → 小写去重 → 截断 90 词。这保证三段来源的词汇不重复，且提示词长度有上界（`PROMPT_MAX = 3000`，超出截断）。

设计要点：①的章级缓存使得翻页时只需计算②；LLM 摘要失败时正则兜底保证流水线永不中断。

## 四、多渠道竞速调度

### 4.1 竞速算法 raceFirst

生图渠道异构且可靠性参差，单渠道串行等待不可接受。Reader3Pic 把所有可用渠道包装为并行任务，**任一成功即胜出，其余取消**：

```kotlin
suspend fun raceFirst(deferred: List<Deferred<T?>>, ok: (T?) -> Boolean): T? {
    val winner = CompletableDeferred<T?>()
    val mainJob = scope.launch {
        val done = mutableListOf<Deferred<T?>>()
        while (done.size < deferred.size) {
            val (d, r) = select {
                deferred.filter { it !in done }.forEach { p -> p.onAwait { p to it } }
            }
            done.add(d)
            if (ok(r)) { winner.complete(r); return@launch }
        }
        winner.complete(null)          // 全部失败
    }
    val result = winner.await()
    mainJob.cancel()
    deferred.filter { it.isActive }.forEach { it.cancel() }   // 取消输家
    return result
}
```

竞速分两层：**渠道族之间**（agnes 族 / omni 族 / 本地族…）先竞速，**族内组合**（key×模型）再竞速。外层再套一个整体超时 `withTimeoutOrNull(115s)` 兜底，保证任何情况下不会无限转圈。

### 4.2 模型级 ETA 调度器

竞速解决了"谁快用谁"，但没有解决"让谁上场"。如果让慢模型占满并发闸，快模型会排队饿死。因此每个 `(服务器, 模型)` 维护最近 5 次实测出图耗时：

```kotlin
modelTimes["$base|$model"] = ArrayDeque(5)   // 成功记实际值；≥5s 的真实慢失败也记

调度流程（每次生图）:
  candidates = 所有可用 (服务器, key, 模型) 组合
  for c in candidates:
      c.eta = avg(modelTimes[c]) 或 ETA_UNKNOWN(60s)   // 无数据者排后
  candidates.sortBy(eta)
  wave = candidates.take(WAVE)        // 只让最快的 2 个组合上场
  raceFirst(wave.map { async { generate(it) } })
```

三个细节值得强调：

- **慢失败的代价**：超时/挂起（≥5s）计入样本，慢模型 ETA 变大，下一轮自动让位；恢复后自动回位，无需人工干预。
- **采样公平性**：全部无数据时按 seed 轮换选模型，保证每个模型都被采样过；同速差异 <1s 的模型间轮换，避免永远打同一个。
- **FIFO 信号闸配合**：并发闸按先来先服务发放，ETA 排序决定了"谁先排队"，两者叠加实现"最快的组合先占闸先开跑"。

### 4.3 omni 网关的同上游归一

win/cat 网关存在"域名 + tailscale IP"双候选（部分安卓 ROM 的 MagicDNS 解析不稳）。它们指向同一台服务器，若各自独立限 2 并发，实际对上游产生 4 并发——慢模型会占满全部闸位，堵死快模型（实测教训：mybestvision 单张 120s+，曾让 flux.1-schnell 的 4.5s 快图全灭）。归一规则：

```
upstream(hostName) = if (hostName == "win-local") "win" else hostName
per-upstream Semaphore(2)
```

## 五、资源约束下的限流与排队

免费 API 普遍实施风控：瞬时高并发触发 429 限流甚至账号封禁。Reader3Pic 的经验是——**限流不是性能敌人，而是可用性前提**。

### 5.1 双层限流

```
并发闸（信号量）:  每 host Semaphore(2)   —— 同一服务器同时最多 2 个在途请求
滑动窗口限流:      每 host ≤ 8 次/分钟     —— 超出部分排队等待，不丢弃

rateGate(url):
  q = requests[host]
  loop:
    now = currentTime()
    淘汰 q 中超过 60s 的旧请求
    if q.size < 8: q.push(now); return        // 获得许可
    else: wait = 60s - (now - q.first) + 200ms // 等最旧请求滑出窗口
    delay(wait)
```

滑动窗口严格保证任意 60 秒窗口内请求数 ≤8，且**排队不丢弃**——预读任务在额度恢复后自动放行。

### 5.2 限流的全覆盖

一个容易漏掉的坑：限流必须覆盖**所有**会打到该服务器的路径。Reader3Pic 中 agnes 的三条路径（生图请求、模型发现 `/v1/models`、组合恢复探测）全部经过同一个滑动窗口闸。任何一条漏网，风控照样触发。

### 5.3 健康管理与指数退避

每个 `(服务器, key)` 组合维护健康状态：

```
单次耗时 > 90s（或异常） → slowStreak++
连慢 2 次 → 下线，安排恢复探测：60s 后
探测成功 → 立即恢复；探测失败 → 退避翻倍，封顶 30min
```

配合每 30 秒一轮的恢复探测循环，被下线的组合最终都会自动归队。路由级另有 45s 短冷却（连续 2 次失败），处理瞬态抖动。

## 六、阅读节奏自适应：让图追上翻页的人

这是整套系统最有意思的部分。设：

- `R` = 读者平均单页阅读耗时（最近 10 次翻页间隔的均值）
- `G` = 生图平均耗时（最近 6 次结果的均值，含真实慢失败）

### 6.1 稀疏生成算法

当 `G ≤ R`，每页都生成。当 `G > R`，每页生成必然积压——全部排队、全部超时、一张也等不到。Reader3Pic 的选择是**稀疏化**：

```
stride = ceil(G / R)，封顶 10
锚点页 = 与当前页距离为 stride 整数倍的页
生成集 = { 当前页 } ∪ { 锚点页 }
```

例：读者 10 秒翻一页，生图 70 秒一张 → stride = 7 → 每第 7、14、21…页提前生成。读者翻到锚点页时，那张图已经生成了约 70 秒——**恰好就绪**。中间的页没有图（显示缓存的马赛克背景），但"少而准时"远胜于"多而全迟"。

两个工程细节：

- **锚点稳定性**：锚点按"与当前页的距离"定义，用户逐页前进时，同一锚点页始终留在预取窗口内，任务不会被翻页 diff 取消。
- **窗口扩展**：预取窗口必须 ≥ 2×stride，否则锚点页在窗口外，永远轮不到提前生成。

### 6.2 动态分辨率决策

分辨率是质量与速度的旋钮。`decideSize` 综合三个信号：

```kotlin
decideSize(keys):
  allReady  = 窗口内所有页都有缓存
  noneReady = 窗口内一页缓存都没有
  avg       = G；tooSlow = (R < G)      // 看图等不及

  when:
    allReady && (G 无数据 || G ≤ 30s) && !tooSlow → 1024×1024   // 快且全就绪，质量优先
    allReady                                      → 768×768    // 全就绪但偏慢，别贪
    noneReady && tooSlow                          → 768×768    // 落后追赶，用最低档
    else                                          → 768×768
```

注意下限即 768：上游模型对 512 等尺寸直接拒绝（HTTP 422），档位必须迁就能力边界。

### 6.3 失败页补图

生图失败的页记录失败时间戳，进入 60 秒退避；此后每 30 秒的补图循环重新排队，直到出图。这意味着**渠道恢复后，无需读者做任何操作，缺的图会自己补上**。秒回失败（渠道全冷却时毫秒级返回）不计入耗时统计——否则毫秒级样本会把均值拉低，系统误判"生图很快"而排满任务，形成恶性循环。这个反例说明：**自适应系统的每个反馈信号都必须有正确的语义边界**。

## 七、探测与自愈

### 7.1 渠道探活与双候选

后台探活循环按自适应节奏运行：断链时 30 秒快扫，全健康时 2 分钟慢扫。探测规则：任何 HTTP 响应（含 5xx）视为服务存在，但 **401/403 视为不可达**——key 无效的服务器"可达"毫无意义（实测教训：曾把返回 401 的网关判为可用，生图全灭后才定位）。

### 7.2 内置基准测试

调度器的 ETA 需要数据。被动等待真实阅读采样太慢，Reader3Pic 增加**主动基准测试**：阅读空闲时（无生图任务），每 10 分钟实测一个 `(服务器, 模型)` 组合——agnes 用户 key×模型、omni 网关×模型、本地模型全覆盖轮换。基准请求走正常生图路径，天然受并发闸与限流闸约束。数轮之后，调度器对全部模型拥有新鲜的 ETA，无需读者做任何事。

### 7.3 统计持久化

所有统计（模型耗时窗口、阅读速度窗口）持久化为 <10KB 的 JSON，记录时即时保存。重启后调度器立即拥有完整延迟画像，不用从零摸索。

## 八、等待体验设计：马赛克与雾

生图期间窗口显示的不是黑屏或空转，而是"相关缓存图 4×4 马赛克拼图 + 半透明白雾"：

- 从缓存中按 `|章节差|×10⁶ + |页位置差|` 排序取相关度最高的 16 张图拼合；
- 每 30 秒轮换更替；
- 白雾（α≈0.6 的白色覆盖层）保证拼图退为背景、不干扰阅读。

这来自一个朴素的设计判断：**等待本身无法消除，但等待的观感可以设计**。拼图素材取自"这本书最近的画面"，读者在等待时看到的是这本书的视觉记忆，而不是无关的加载动画。

## 九、多维度分析

### 9.1 性能维度：等待时间的下界与调度增益

生图等待时间的理论下界 = 最快渠道的生图耗时。调度系统的价值在于**逼近这个下界的概率**：

- 无调度：任一渠道都可能被选中，若慢渠道占闸，实际等待 = 慢渠道耗时（实测教训：120s 慢模型堵闸后，4.5s 快模型全灭）。
- ETA 调度 + FIFO 闸：最快组合先占闸，实际等待 ≈ min(最快模型耗时, 队头延迟)。
- 限流排队是等待时间的另一来源：预算 8 次/分钟内，排队延迟可控；超限部分按窗口滑动延迟释放。

一个量化的例子：读者 8 秒/页，qwen 本地 64s/张 → stride = 8 → 每 8 页一张准时就绪；当 cat 网关 schnell（4.5s）可用时，avg(G) 下降 → stride 回落 → 每页都有图。**调度系统的输出是阅读体验的连续谱，而非开关**。

### 9.2 体验维度：稀疏生成的取舍

稀疏生成本质是在"全有但全迟"与"部分但准时"之间做最优传输。信息论视角：插画对阅读的边际价值随其**时点**衰减——读者已翻过 3 页的图，价值大打折扣。因此"准时"权重高于"密度"。stride = ceil(G/R) 恰好是"图在到达时仍有时效"的最大密度；封顶 10 则防止极端情况下（渠道半瘫）完全放弃生成。

### 9.3 工程维度：故障域隔离与自愈

系统把故障划分为四层，各自独立自愈：

| 层 | 故障 | 自愈机制 |
|---|---|---|
| 请求 | 超时/4xx/5xx | 路由冷却 45s + 组合退避 |
| 组合 | 连慢/封号 | 健康下线 + 指数退避恢复探测 |
| 渠道 | 网关断链/key 失效 | 探活 30s 快扫 + 401/403 即判死 |
| 进程 | 重启 | 统计持久化，重启零冷启动 |

四层互不阻塞：一层故障只缩小候选集，不拖垮整体。实测中 cat 网关 catalog 半瘫、agnes 账号风控、MuMu 虚拟机 NAT 抖动同时发生时，系统仍能靠本地 qwen 维持稀疏出图。

### 9.4 成本与合规维度

限流是双赢设计：上游免于风控封禁（实测一次并发风暴触发过账号临时封禁），下游获得稳定的长期可用性。滑动窗口 + 排队不丢弃的组合，把"限流"从硬失败转化为软延迟——这是与免费 API 打交道的正确姿势。

### 9.5 局限与展望

- **提示词质量上限**：LLM 摘要偶发偏离原意，插画与文字错位。方向：引入图文对齐评分，低分图静默重生成。
- **稀疏生成的内容连续性**：锚点页的插画与前后页可能风格漂移。方向：以章节级种子保持风格一致。
- **隐私考量**：页文本上传云端即离开设备。方向：本地优先调度（本地模型 ETA 加权折扣），云端仅在本地不可用时兜底。

## 十、结语

文生图让"每页有画"从奢侈品变成工程问题。这个问题的核心不是画得多好，而是**画得多么准时**——阅读节奏与生图速度的失配，需要一套从提示词聚合、多渠道竞速、模型级 ETA 调度、双层限流，到稀疏生成、动态分辨率、失败补图、统计持久化的完整调度系统来弥合。Reader3Pic 的实践表明：当一个自适应系统把"读者的耐心"作为一等公民纳入调度目标时，即使底层资源参差不齐，阅读体验也能稳定在"少而准时"的可用区间——而随着底层模型的持续提速，这个区间会自动滑向"多而准时"。
